# Writing back to ORDS from an agentic app

Read-only ORDS integrations fail safely. Writes do not. This reference covers
the pattern for app actions that call ORDS `POST` / `PUT` / `DELETE` handlers:
assign, approve, release, update. Artifact commands and the app/workflow
contracts belong to the base `aistudio` skill; this file covers what is specific
to ORDS writes.

## The shape that works

```
InitActions / Query terminal  ─ emits oraInsight ─►  user clicks
                                                         │
app action (agentCommand, payload as context) ◄──────────┘
        │
        ▼  $context.$app.$OraMessageHint = "InvokeAction"
START → shared ORDS fetches → CODE snapshot → SWITCH(app stage)
                                              └─ InvokeAction
                                                   → CODE  parse + re-validate
                                                   → SWITCH(operation)
                                                        ├─ EXTERNAL_REST write A ─┐
                                                        ├─ EXTERNAL_REST write B ─┤
                                                        └─ RETURN "nothing changed: <reason>"
                                                   → CODE  merge result ◄─────────┘
                                                   → LLM   report outcome
```

1. **Create the app action before writing the prompts that invoke it.** Action
   codes are generated by the app tooling (for example `action1`) and cannot be
   chosen. The InitActions and Query prompts must embed the real code in
   `ora.Invoke("<code>", {...payload...})`.
2. **The payload must be self-contained.** With the payload sent as context,
   the step's command is ignored. Include `operation`, the record keys, the
   target (for example `assignee`), and a one-line `instruction`.
3. **Re-validate against fresh data before writing.** The InvokeAction route
   runs the same shared fetches as the display stages. Use them: in the parse
   CODE node, drop keys that no longer exist or are no longer in a writable
   state. Reject targets that are not active, and refuse changes that would
   discard work in progress. A suggestion computed minutes ago is not proof the
   write is still valid.
4. **Route invalid requests to a `RETURN`** with the reason. Nothing is sent to
   ORDS.
5. **Merge branch outputs in one CODE node** before the reporting LLM, using
   optional access for the branch that did not run. Don't reference
   branch-local nodes directly from the LLM.
6. **Add a refresh step to the action** (refresh agents plus priority actions)
   so panels reflect the write.

Clicking a specific, clearly titled action ("Assign TKT-1001 to j.rivera") is
the user's confirmation. Keep titles unambiguous: name the record and the
target.

## Make the ORDS handler honest

Agents report what the handler returns. Common handler patterns mislead them:

| Handler pattern | What the agent will say | Fix in PL/SQL |
|---|---|---|
| `UPDATE … WHERE status = 'OPEN'` then an unconditional audit `INSERT` and `count := count + 1` | "3 records updated" when 0 were | return `SQL%ROWCOUNT` from the `UPDATE`, not a loop counter |
| action label decided once per batch (`IF action = 'ASSIGN' THEN action := …`) | wrong audit type for later rows in the same call | decide per row, in a local variable |
| `WHEN OTHERS THEN :status := 500; HTP.P(SQLERRM)` | raw ORA- text in the chat | map known errors to `400` / `404` with a short message; keep `SQLERRM` in a log table |
| success response with no identifiers | "Done" with no detail | echo the keys changed and the new state |

Return a small JSON object with `success`, `updated_count`, the affected keys
and `message`, and declare it in the write node's `outputSpecification`.
[../assets/example/06-write-handler.sql](../assets/example/06-write-handler.sql)
shows the pattern.

## Testing writes

- **Live recording of InvokeAction performs the write.** The test sync plan
  schedules a live recording of one representative InvokeAction payload. Point
  it at a non-production pod and ATP, or at a record created for the test.
  Say so in the test notes.
- Cover the `RETURN` rejection route with a baseline-derived test that
  overrides the fetch so the requested key is gone. That needs no live write.
- Re-running the same assignment should be harmless: the handler updates 0
  rows, or reports "already assigned". Test that the report says so.

## Checklist

- [ ] App action created first; prompts embed its generated code
- [ ] Payload carries operation, keys, target and instruction
- [ ] Parse node re-validates every key and target against the fresh fetch
- [ ] Invalid requests end in a `RETURN`; no ORDS call
- [ ] Handler returns real affected-row counts and keys
- [ ] Write recording runs against non-production data or a dedicated test record
